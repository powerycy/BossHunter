# 并行采集设计

## 目标

- 全流程中的 AI 评分继续复用现有 `scoring_concurrency` 并发评分器。
- 采集按“城市 × 搜索关键词”拆分为独立任务并行执行。
- 新增采集并发配置，默认 1，允许 1-3。
- 采集结果、去重和新增岗位 ID 汇总后再进入 AI 评分。

## 方案

保留当前单任务的分页和详情抓取顺序，将每个城市/关键词组合交给一个采集 worker。每个 worker 创建自己的数据库连接，浏览器请求继续使用独立 target ID；主线程只负责提交任务、收集结果和合并 `new_job_ids`。并发数通过 `search.collection_concurrency` 读取并限制在 1-3，设置为 1 时等价于旧的串行行为。

采集 worker 发生异常时只记录该组合失败并继续其他组合。停止事件会阻止新任务提交，已运行的浏览器任务在当前页面操作结束后清理 target 并退出。命令行显式传入全局数量上限时，保持串行采集以确保严格遵守上限。

## 数据一致性

- 每个 worker 使用独立 SQLite 连接，避免在线程间共享连接。
- 现有 `INSERT OR IGNORE` 和 job ID 去重规则保持不变。
- `new_job_ids` 在主线程合并，采集完成后只对本次新插入岗位调用 AI 评分。
- 采集失败不影响其他组合，也不会触发对旧岗位的评分。

## 配置与界面

在搜索设置增加“采集并发数”下拉选项 `1/2/3`，默认 `1`，并明确提示提高并发可能触发平台风控，甚至导致账号限制或封号。

## 测试

- 配置缺失、非法和边界值归一化为 1-3，缺失默认 1。
- 多个采集组合确实同时运行，且每个组合拥有独立连接。
- 任意一个组合失败时其他组合仍完成，并记录失败日志。
- 全流程在采集汇总完成后才开始评分，并且只传递新增岗位 ID。
- 停止任务不会继续提交新的采集组合。

## 最终确认

采集并发默认值为 `1`，允许范围为 `1-3`。设置界面必须提示：提高采集并发可能触发平台风控，甚至导致账号限制。
