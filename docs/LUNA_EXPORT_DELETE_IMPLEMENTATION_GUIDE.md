## 3. 已确认的产品行为

### 3.1 三种导出范围

必须提供且严格区分：

1. **导出全部岗位**
   - 导出当前岗位池内所有未软删除岗位。
   - 不受搜索、城市、状态筛选和前端分页影响。
2. **导出筛选结果**
   - 导出符合当前搜索词、城市、状态等筛选条件的所有未软删除岗位。
   - 必须由后端按数据库和结构化筛选参数查询，不能只导出当前表格页，也不能依赖前端把岗位对象传回后端。
3. **导出所选岗位**
   - 只导出用户明确勾选的未软删除岗位 ID。
   - 选择可以跨表格分页保留。
   - 空选择必须在前端禁用，后端也必须拒绝。

CSV 和 XLSX 都必须支持三个范围。继续保持：

- CSV 使用 UTF-8 BOM。
- CSV 保留公式注入防护。
- CSV/XLSX 包含完整岗位 URL。
- XLSX URL 是可点击超链接。
- 导出接口只根据数据库行生成内容，不信任前端传入的岗位标题、公司、JD、URL 等字段。
- 已软删除岗位默认不能通过 `all`、`filtered` 或过期的 `selected` ID 混入普通导出。

### 3.2 软删除与回收站

- 每个岗位行提供“删除”入口。
- 支持勾选多个岗位后批量删除。
- 普通删除是软删除：岗位从默认岗位池隐藏，但数据库记录和关联历史继续保留。
- 增加“回收站/已删除岗位”入口，能够查看软删除岗位。
- 回收站支持单条恢复和批量恢复。
- 恢复后保留岗位删除前的业务状态、评分、招呼语、链接和历史，不自动评分、生成、发送或访问 BOSS。
- 软删除已发送或已回复岗位时允许继续，但必须使用明确警告和二次确认，并保留发送/回复历史。
- 软删除岗位不得再进入采集目标计数、待评分、待确认、招呼语生成、发送、恢复任务派发或监测执行队列。
- 已删除岗位不能因为再次采集到相同 ID/URL 而被静默新建或自动恢复；恢复必须由用户主动操作。

### 3.3 永久删除

- 回收站支持单条永久删除和批量永久删除。
- 永久删除不可恢复，前端必须使用比软删除更醒目的确认文案。
- 后端必须要求明确确认字段，不能只依赖前端弹窗。
- 已发送、已回复、已发简历、待手动发简历、已跟进，或历史中已经存在发送/回复证据的岗位，禁止永久删除，只允许软删除。
- 保护判断不能只看当前 `status`；还要检查历史动作，防止状态后来变化后绕过保护。
- 普通未发送岗位永久删除时，必须在事务内按依赖顺序删除相关历史和岗位记录；任何一步失败都要整体回滚。
- 永久删除前审计所有直接或间接的 `job_id` 引用。不要通过字符串替换破坏任务 JSON。
- 处于运行中、暂停中或可恢复任务 checkpoint 中的岗位不得被永久删除；后端应返回结构化冲突信息，提示用户先结束相关任务。

## 5. 推荐接口与数据契约

允许在不破坏兼容性的前提下调整命名，但前后端和测试必须保持一致。

### 5.1 岗位列表

建议扩展现有接口：

```text
GET /api/jobs?deleted=active|only|all&status=...&city=...&q=...&limit=...&offset=...
```

- 默认 `deleted=active`，只返回未软删除岗位。
- `deleted=only` 用于回收站。
- `deleted=all` 仅在确有内部需要时使用，不作为普通岗位池默认值。
- `X-Total-Count` 必须与相同删除范围和筛选条件一致。
- 非法 `deleted`、`limit`、`offset` 返回 400。

将岗位筛选 SQL 提取为可复用的数据层/查询模块，供列表和导出共同使用，避免两套筛选语义漂移。

### 5.2 导出

保留：

```text
POST /api/jobs/export
```

建议请求契约：

```json
{
  "format": "xlsx",
  "scope": "filtered",
  "job_ids": [],
  "filters": {
    "q": "Python",
    "status": "ready",
    "city": "北京"
  }
}
```

规则：

- `scope=all`：忽略 `job_ids` 和普通筛选，只查询全部未删除岗位。
- `scope=filtered`：忽略 `job_ids`，后端规范化并应用 `filters`。
- `scope=selected`：要求非空、去重后的 `job_ids`，忽略 `filters`。
- 非法 scope、format、筛选类型、空 selected、超量 ID 返回 400 和结构化错误。
- 返回成功时可增加 `X-Exported-Count`，前端使用后端真实数量提示，不能使用估算数量。
- 对过期、已删除或不存在的 selected ID，要么明确拒绝并返回无效 ID，要么只导出有效项并返回 `skipped_ids`；必须选择一种明确行为并写测试，不能静默把“导出 2 条”变成“导出 1 条”却仍提示 2 条。优先建议整体拒绝，便于用户发现选择状态已过期。

### 5.3 软删除、恢复、永久删除

建议使用批量动作接口，单条操作传一个 ID，避免维护两套逻辑：

```text
POST /api/jobs/soft-delete
POST /api/jobs/restore
POST /api/jobs/permanent-delete
```

请求示例：

```json
{
  "job_ids": ["job-a", "job-b"],
  "confirmed": true
}
```

永久删除可再要求强确认值，例如：

```json
{
  "job_ids": ["job-a"],
  "confirmed": true,
  "confirmation": "PERMANENT_DELETE"
}
```

后端要求：

- `job_ids` 必须是非空数组，去重、去空并设置合理批量上限。
- 未传确认字段返回 400，不执行任何修改。
- 返回 `requested_count`、`affected_count`、`blocked`、`not_found` 等结构化结果。
- 批量永久删除遇到受保护岗位时，优先整体拒绝和回滚，避免用户误解为全部删除成功。
- 软删除已删除岗位、恢复未删除岗位应保持幂等并返回准确数量。
- 所有写操作必须由数据库事务保证一致性。

## 6. 数据库兼容迁移

建议在 `jobs` 表增加：

```text
deleted_at TIMESTAMP NULL
deleted_reason TEXT NULL
```

可以根据实现需要增加受控字段，但不要把原业务状态改成一个笼统的 `deleted` 状态；使用独立 `deleted_at` 可以让恢复后自然保留删除前的状态。

迁移要求：

- 沿用 `db.py` 中现有 `_migrate_v1_*` 的幂等向前迁移方式。
- 不清库、不重建真实数据库、不丢失旧字段。
- 旧数据库首次打开后新增字段，原记录默认未删除。
- 重复执行迁移不报错、不重复改写、不丢数据。
- 建议增加 `deleted_at` 相关索引，但必须使用 `IF NOT EXISTS`。
- 所有迁移实验仅使用 `tempfile.TemporaryDirectory()` 下的临时 SQLite。
- 不得对 `data/bosshunter.db` 执行迁移试验，也不得读取其中内容。

## 8. 必须覆盖的测试场景

### 8.1 导出

- 8 个岗位中筛选命中 3 个，导出筛选结果恰好是这 3 个。
- 勾选任意 2 个岗位，导出所选恰好是这 2 个。
- 导出全部包含所有未删除岗位。
- 软删除 1 个岗位后，普通全部/筛选/所选导出都不能混入该岗位。
- 空 selected、非法 scope、非法 format、非数组 ID、超量 ID 被后端拒绝。
- 前端筛选条件改变后，导出使用点击时的最新条件。
- CSV 使用 BOM 且具有公式注入防护。
- XLSX URL 可点击，CSV/XLSX 均保留完整 URL。
- 导出只从数据库读取，不接受前端伪造的岗位内容。

### 8.2 删除与恢复

- 单条软删除后默认岗位池消失，回收站出现。
- 批量软删除返回准确数量。
- 恢复后回到原状态，评分、招呼语、链接和历史保留。
- 连续两次软删除/恢复行为幂等且数量准确。
- 刷新页面后状态不丢失。
- 删除后前端勾选状态被清理。
- 软删除岗位不进入评分、招呼语、发送和恢复任务队列。
- 重复采集相同岗位不会自动恢复。

### 8.3 永久删除保护

- 普通 pending/filtered/ready 且无发送历史岗位可永久删除。
- sent、replied、resume_sent、needs_resume、follow_up_sent 等岗位不可永久删除。
- 当前状态普通但历史中存在发送/回复动作的岗位不可永久删除。
- 未传 `confirmed=true` 或强确认值时后端拒绝。
- 批量中混入一个受保护岗位时整个事务不产生部分删除。
- 活跃或暂停任务 checkpoint 引用的岗位不能永久删除。
- 永久删除成功后相关直接历史按设计清理，不留下违反外键或查询异常的数据。

## 9. 安全与禁止事项

- 所有数据库测试必须使用临时 SQLite。
- 不得打开、读取、复制、备份、迁移或修改用户真实 `data/bosshunter.db`。
- 不得读取或输出真实简历正文。
- 不得读取、显示或写入 API Key、Cookie、OAuth、Token、登录状态和浏览器凭据。
- 不得启动真实 BOSS 采集、评分、招呼语生成、发送或监测。
- 不得运行真实批量 AI 请求。
- 不得改变发送前人工确认原则。
- 不得让删除功能绕过验证码、账号异常、平台拦截或频率限制。
- 不得通过删除测试、降低断言、吞掉异常或只改前端提示制造“通过”。
- 不得将真实数据库、简历、导出文件、配置、日志或凭据加入 Git。

## 10. 最终报告格式

10. 前端两次或多次构建以及最终构建结果。
11. 临时 SQLite 迁移、导出、删除、恢复和永久删除冒烟结果。

14. 是否访问或修改真实数据库、简历、导出数据或凭据。
15. 修改和新增的关键文件。
16. 尚存限制和需要用户手动验证的事项。
17. `git diff --check` 真实结果。
18. 当前分支和完整 `git status --short --branch`。

不要只回答“已完成”或“测试通过”。没有实际运行的项目必须标记“未验证”，历史测试结果不能当作本轮证据。
